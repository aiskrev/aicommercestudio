# Производителност: независимо измерване, анализ и промени (одит 2026-11-12, фаза 08)

**Кратък извод.** Вътрешният отчет сочи мобилен LCP 3,10–4,08 s. Измерих го независимо и получих същото (3,37–3,81 s на `/bg`) при симулирано ограничаване, но при **приложено** ограничаване на мрежата и процесора (реално забавяне в браузъра, не изчисление) LCP беше 2,56–2,72 s. След две промени той е 2,27–2,38 s в четири от шест пробега, 2,65 s в един и 3,0 s в един (студен старт; първи пробег след рестарт на сървъра). **Целта ≤ 2,5 s (p75) не е доказана:** лабораторните измервания са върху една машина и не са полеви данни. INP не е измерван (няма инструмент за реални потребители). CLS остана ≤ 0,02.

## 1. Метод (повторяем)

* Код: състоянието на клона на одита (преди = `88aed98`, след = комити `d68b14a` и по-късно), производствен билд (`docker compose up --build`), собствен стек `acs-audit` върху Docker Desktop на Windows 11, мрежата на Docker (`http://web:3000`, HTTP/1.1, без TLS, без CDN).
* Инструмент: Lighthouse 13.5.0 в Playwright контейнера, мобилен профил (Moto G Power, 4× процесор).
* **Два режима, и двата са записани, защото дават различни числа:**
  1. *Симулирано* (стандартното на Lighthouse, `scripts/lighthouse.ps1`): наблюдава се зареждане без ограничаване и после се **изчислява** какво би било при бавен 4G. Скриптът за това е `e2e/perf/lighthouse.mjs`.
  2. *Приложено ограничаване* (`--throttling-method=devtools`): браузърът наистина е бавен (1,6 Mbps, 150 ms RTT, 4× процесор) и метриката е **наблюдавана**. Скриптът е в [Приложение А](#приложение-а-скрипт-за-приложено-ограничаване).
* 3 пробега на адрес. Машината не беше празна при всички (виж бележките), затова разликите под ~0,3 s са шум.
* Не е измерено: реални устройства, TLS/HTTP/2/HTTP/3 и сжатие през Cloudflare, кеш на ръба, полеви данни (CrUX), INP.

## 3. Анализ: какво определя LCP

1. **LCP елементът** е `h1.t-hero` (текст, без изображение). Времето за първи байт е ~35 ms; всичко останало е „закъснение на изобразяването“.
2. **Симулираното 3,4–3,8 s** идва от модела на Lighthouse: при наблюдавани 379 ms (без ограничаване) той добавя изпълнението на скриптовете и оформлението, което се случва преди първото рисуване, умножено по 4 за процесора. Главната нишка: Script Evaluation 900 ms, Style & Layout 646 ms, Other 1 393 ms (при 4×). Затова симулираният LCP е чувствителен към обема на изпълнявания JavaScript и на DOM.
3. **Приложеното ограничаване** показа истинското тясно място: след изтеглянето на документа (57 KB, 0,9 s) браузърът намира едновременно **шест шрифта за предзареждане (≈158 KB)** и **два CSS файла (27 KB, блокират рисуването)**; всички делят 1,6 Mbps и CSS завършва едва към 2,0–2,2 s, а FCP/LCP е около 2,6 s. Предзареждането на шрифтове не е нужно за първото рисуване (`font-display: swap`).
4. Неизменено от предишната работа и вече положително: `content-visibility: auto` за секциите под сгъвката (`.fc-defer`), без външни скриптове и шрифтове, без анимация върху H1.

## Приложение А: скрипт за приложено ограничаване

```sh
npm install --global lighthouse@13.5.0
export CHROME_PATH=$(ls -d /ms-playwright/chromium-*/chrome-linux*/chrome | tail -1)
lighthouse http://web:3000/bg --output=json --output-path=/out/dt_bg_1.json --only-categories=performance \
  --throttling-method=devtools --chrome-flags="--headless=new --no-sandbox --disable-dev-shm-usage"
```

Пуска се в `e2e` контейнера на тестов стек (`docker compose -p <име> --profile test run --rm --no-deps e2e …`), три пъти на адрес; резултатите са в `apps/web/e2e/perf-results/` (не се комитват).
